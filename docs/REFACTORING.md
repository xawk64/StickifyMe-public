# Подготовка к публикации: что изменено и почему

Код писался как продукт: быстро и под production-окружение. Перед публикацией он прошёл
рефакторинг. Цель была сделать проект безопасным, запускаемым у любого и удобным для чтения,
не переписывая его с нуля и не меняя стек (Next.js, Express, MongoDB). История коммитов
сохранена; каждое изменение — отдельный коммит в формате conventional commits.

Порядок работы: сначала **инфраструктура для проверки** (тесты, линтер, CI), затем
**безопасность** (каждая уязвимость сначала воспроизводится тестом), потом **зависимости**,
**TypeScript и слои**, **интеграция с Wildberries** и **локальный запуск**.

## 1. История и секреты

- Из истории git удалены файлы окружения и сгенерированные артефакты, токены и пароли
  заменены на `***REMOVED***`, автор коммитов приведён к одному имени. Проверка: gitleaks по
  всей истории и поиск по регулярным выражениям.
- Все ключи, которые когда-либо были в репозитории, считаются скомпрометированными и подлежат отзыву.
- Удалены конфигурация деплоя на прод-сервер, nginx-конфиг, сгенерированные sitemap и счётчики
  аналитики. Домен, e-mail и имя бота вынесены в переменные окружения с нейтральными значениями.

## 2. Инфраструктура разработки

| Было | Стало | Зачем |
|---|---|---|
| Ни одного теста | Vitest + supertest + mongodb-memory-server, ~100 тестов | Менять код безопасно; каждая уязвимость закреплена тестом |
| Линтер только на фронте | ESLint (typescript-eslint strict) + Prettier для API | Единый стиль, запрет `any` и `console` |
| Только CD на прод-сервер по паролю root | CI: lint, typecheck, тесты, сборка образов | Каждый коммит проверяем |
| Docker под root, без healthcheck, MongoDB наружу | Multi-stage образы, non-root, healthchecks, MongoDB только во внутренней сети | Минимальная поверхность атаки, предсказуемый старт |
| Нет `.env.example` | Документированный `.env.example`, конфиг валидируется zod на старте | Ошибка конфигурации видна сразу, а не через `undefined` |

## 3. Безопасность

| Проблема | Последствие | Исправление |
|---|---|---|
| Эндпоинт профиля отдавал любой профиль, а с `?page=` — все профили с WB-ключами | Утечка ключей всех продавцов любому залогиненному | Эндпоинт удалён (клиент его не использовал) |
| Листинг истории этикеток без фильтра по пользователю | Утечка заказов всех продавцов | Удалён; осталась постраничная история своего пользователя |
| «Опциональная» авторизация вызывала `next()` дважды | Без токена отдавалась чужая история, с битым токеном падал обработчик | Обычная авторизация на всех эндпоинтах этикеток |
| PDF писался в общий файл `stickers.pdf` | При параллельной генерации можно было получить чужие этикетки | Генерация в память для каждого запроса |
| Имя файла аватара из запроса входило в путь, тип не проверялся | Path traversal, stored XSS через HTML/SVG | Имя генерирует сервер, тип определяется по сигнатуре, лимит 2 МБ, `nosniff` |
| Тело запроса целиком записывалось в профиль | Mass assignment (`chatId`, `avatarUrl`, ...) | zod-схемы с белым списком полей |
| Данные запроса без проверки уходили в запросы MongoDB | NoSQL operator injection: выдача токена сброса пароля чужому аккаунту | zod-валидация всех входных данных |
| HTML писем собирался из пользовательского ввода | HTML-инъекция в письма | Шаблоны с экранированием |
| Разные ответы «нет пользователя» и «неверный пароль», bcrypt cost 8, нет rate limit, токены сброса в открытом виде | Перебор аккаунтов и паролей | Единый 401, dummy-hash для одинакового времени ответа, cost 12, rate limit, SHA-256 токенов |
| Telegram привязывался по id пользователя | Чужой чат мог получать уведомления продавца | Одноразовый токен (в БД только хэш) |
| WB-ключ хранился открытым текстом и отдавался в браузер, браузер сам ходил в WB | Компрометация ключа при XSS или утечке БД | AES-256-GCM, проверка ключа на сервере, клиент видит только `hasWbApiKey` |
| JSON до 50 МБ на любом эндпоинте | Лёгкий DoS по памяти | 1 МБ по умолчанию, 50 МБ только для этикеток |
| Неиспользуемый геокодер отправлял WB-ключ стороннему сервису | Утечка ключа третьей стороне | Удалён |

Найденные по пути баги: регистрация отвечала до сохранения профиля, и мгновенный вход падал;
одновременные регистрации создавали дубли (добавлены уникальные индексы); необработанный
rejection в мониторинге останавливал сервер; сообщение без текста (стикер, фото) в бот ронял
процесс; на этикетку могли попасть номера стикера другого заказа; после успешной регистрации
показывалась ошибка из-за не загруженного скрипта аналитики.

## 4. Зависимости

mongoose 5 → 8, jsonwebtoken 9, bcryptjs 3, nodemailer 10, pdfkit 0.17, Node 18 → 22 LTS,
Next.js до последнего патча 14.2, TypeScript 5. Удалены неиспользуемые пакеты (redis, socket.io,
qrcode, uuid, body-parser, webpack-лоадеры, canvas2pdf, xlsx). У API нет high/critical advisories;
оставшиеся advisories фронта относятся к ветке Next 14 и разобраны в
[dependency-audit.md](dependency-audit.md).

## 5. TypeScript и слои

- API переведён с JavaScript на TypeScript strict (`noUncheckedIndexedAccess`) по одному модулю
  на коммит; на время перехода тесты гонялись против собранного кода, чтобы приложение и тесты
  использовали один экземпляр mongoose.
- Слои: routes → тонкие controllers → services → repositories. Бизнес-логика (регистрация с
  компенсацией при сбое, импорт, мониторинг) больше не живёт в HTTP-обработчиках.
- Раскладка PDF вынесена из контроллера в модуль `labelPdf`; совпадение вывода со старой версией
  проверено сравнением content-стримов PDF.
- Синглтоны, создававшиеся при `require`, заменены composition root: все зависимости создаются
  в `index.ts` и передаются явно. Это и сделало возможными фейки в тестах.
- `console.*` заменён на pino (структурированные JSON-логи, редактирование секретов, request-логи).

## 6. Интеграция с Wildberries

- Вызовы API WB перенесены из браузера на сервер, в типизированный `WbClient`: таймауты, retry
  с экспоненциальной задержкой и jitter, учёт `Retry-After` для 429, zod-валидация ответов,
  доменные ошибки.
- Импорт заказов выполняется на сервере и передаёт прогресс потоком NDJSON.
- Мониторинг: проверки одного профиля не накладываются; при отозванном ключе мониторинг
  останавливается с одним уведомлением; Telegram-сообщения экранируются и делятся по лимиту длины;
  мониторинг стартует сразу после привязки чата.

## 7. Запуск у любого

`docker compose up --build` поднимает фронт, API, MongoDB, мок WB API с эмуляцией 429/5xx/таймаутов
и заполняет демо-данные. Без токенов Telegram и SMTP приложение работает и пишет сообщения в лог.

## Что сознательно не менялось

- Стек и общая архитектура (Next.js Pages Router + Express + MongoDB).
- Поведение для пользователя, кроме исправленных ошибок и безопасности: тексты, раскладка этикеток,
  правила мониторинга.
- Предупреждения `react-hooks/exhaustive-deps` на фронте: исправление меняет момент выполнения
  эффектов и требует ручной проверки UI.
- Мажорное обновление Next.js 14 → 15: это отдельная задача, она описана в
  [dependency-audit.md](dependency-audit.md).
